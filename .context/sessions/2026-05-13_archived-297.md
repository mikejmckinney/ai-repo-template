## Harder Than Expected
- **24 rounds of bot review on what shipped as a docs-only PR** is far above the typical 3–9 rounds the project has historically converged in. The bulk of late-round noise (R10–R21) was on `scripts/diag-hang-snapshot.sh`, a tertiary deliverable added mid-PR for diagnosing fan-out hangs. Each round surfaced a slightly-different concretization of "the diagnostic script could be more portable / more defensive / less locale-dependent": mawk vs. gawk for `awk 'NR==1 || …'`, `top -w200` not supported on busybox, `ss` exit codes leaking into the loop, `mkdir -p` returning silent success on conflict, `OUTDIR` default polluting `/tmp`, etc. The right framing is that the diagnostic script became a magnet for bot attention precisely because it's the kind of code where every choice is defensible-but-not-uniquely-correct — a class that benefits from a `## Caveats` block in the script header up front rather than rounds of incremental rationale comments.
- **Two thread-author identities dominated the late rounds.** gemini-code-assist contributed roughly 70% of R10–R21 findings; chatgpt-codex-connector contributed the load-bearing R8 + R9 structural findings (consensus-candidate overlays missing from `MULTIAGENT_FILES` + `REQUIRED_FILES`, candidate-overlay `write` tool grant). The defer-with-citation pattern from PR #292's R5–R7 worked again here for gemini's regex-tightening cycle (R10 onward) — explicit rationale comments + a one-line styleguide skip-class entry consistently halted the cycle within 1–2 rounds.
- **The `merge-if-ready` workflow can't auto-merge a Judge-only-approved PR.** It requires a human reviewer approval to satisfy the branch protection rule. The Judge subagent's APPROVE verdict is recorded as a comment, not a GitHub review approval. Manual `gh pr merge --admin` worked for this PR; longer-term either Judge needs to post via the PR review API (currently blocked because the Copilot SDK doesn't grant subagents PR-review-write tools) or `merge-if-ready` needs a `judge-approved` label as an alternate signal.

## Generalizable Lessons
- **The R8 Theme-C principle ("`execute` only when shell IS the role's product") is now load-bearing.** It governed both R8 (reverted from analyst/architect/judge/critic) and R22 (extended to docs after the same bot found the same class of issue on a role that wasn't in the original PR scope). Worth promoting from Round 8's commit message into a `.context/rules/agent_ownership.md` or ADR amendment so future role definitions reference the principle by name rather than re-deriving it. Filing as follow-up consideration; not done in this close-out.
- **Two-empty-round termination is a robust signal but is observation-window-bounded.** R23 + R24 fired empty over a 14-minute window; gemini-code-assist + cursor-bugbot review latencies are sub-7-minute on this repo per pipeline observation, so 7-minute waits per round are sufficient. If the bot pool grows or any reviewer's latency increases past ~7 minutes, the empty-round counter could declare convergence prematurely. Worth recording the observed latency upper bound (~7 min) in the operator guide so the wait window can be tuned per-bot-pool.
- **Two-session interactive `pr-resolve-all` runs need a re-orientation step at the start of the resumed session.** The second session reading `git log --oneline origin/main..HEAD | wc -l` to discover "43 commits ahead" plus `gh api graphql ... reviewThreads` to get the current unresolved-thread count was the right first move; without it, the agent risks re-solving issues that were already resolved in the prior session. Worth a one-line callout in `pr-resolve-all.md` that on session resume, the first action is always "count commits + count unresolved threads" before reading any prior comments.
